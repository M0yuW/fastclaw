# V5 quality-development plan (not a frozen confirmatory protocol)

Status: development only; **zero v5 model observations and zero new paid authorization**. The sealed v4 run remains 100/100 recorded, 99 mechanical completions, with its all-20 strict case gate failed. Do not pool, rescore, or replace v4 after the fact.

## Failure-driven engineering changes already checked for free

1. **Tool-write contract.** The finance-tools plugin accepts empty `causal_claims` when no trusted statement-line metadata exists; nonempty unsupported claims still fail. It rejects review fields serialized inside `rationale` with the retriable `malformed_review_payload` code. Twenty-six plugin unit tests pass. A local scripted Gateway replay deliberately makes the malformed call, observes its error in the next provider request, then makes a corrected call; all eight checks pass, with one persisted review, explicit evidence/date, a blocked thesis and an acknowledged alert. This proves wiring and state recovery *if* the model supplies the corrected call. It does not measure autonomous recovery.
2. **Prompt completeness.** The seen HBAN packet's disclosed Q3 gain-on-sale adjustment (628 GAAP income − 24 gain = 604 adjusted; Q2 adjusted comparator 471) is carried into a development fixture. Its two unit tests and nine-check scripted Gateway replay pass. This cannot count as a fresh answer-quality observation because HBAN has already been inspected.
3. **Numeric-claim contract prototype.** `validate_structured_financial_claims_v1.py` verifies only submitted typed assertions against audited baseline/event rows: same-basis deltas, ratio direction, cross-metric delta rank, delta share, cross-basis gap direction and signed delta identity. Development regressions reconstruct eight *known* v4 numeric mistakes as structured assertions (EVTC, FITB, MKTX, NTRS, RELY, SEIC, USB, VRSK); all eight are rejected and corrected counterparts verify. This is a deliberately overfit regression check, **not** evidence that future model answers will express all material claims in this format or that a clean validator result means high-quality insight. It does not assess causal inference, counterevidence, relevance, or free-form prose.
4. **Typed-candidate state gate prototype.** `verify_insight_candidate_v1.py` accepts only a typed candidate with explicit numeric claims, three nonempty interpretation fields and exact asserted ledger state. It derives the canonical review ID, evidence IDs, next-review date, hold, actionability and alert status from the saved state; a mismatch is held. Seven tests using the retained FITB ledger (one test substitutes a qualitative rationale) confirm wrong numbers, an invented date, invented source attachment, missing claim coverage, an unstructured numeric sentence, numeric leakage in saved rationale and a free-form extra field are held. A clean result is labeled only `candidate_for_qualitative_review` with `quality_pass: null`; it is **not** an automatic publication or quality pass. This prototype does not yet prove every material statement in the interpretation is covered by typed assertions.
5. **Free Gateway candidate replay.** The gate rejects digit/currency/percentage-bearing interpretation or saved-rationale text outside typed claims and renders a review card from host-verified numbers plus canonical ledger state. `build_insight_candidate_prompt_v1.py` requests the typed format without prewriting the agent's financial conclusion. The final local scripted Gateway replay on the *seen* FITB packet is `results/2026-10-25-insight-candidate-gateway-replay-v2/`: two independent isolated chains each receive the schema prompt, make four paired finance-tool calls and save one blocked review. A correct candidate reaches `candidate_for_qualitative_review`; one with a false +30 pretax delta and invented review date is held with both issues recorded. All seven checks in each branch pass, the result hash list verifies, and there were zero external provider requests/model observations. Eleven prompt/candidate/validator tests pass. The earlier v1 replay, before schema-prompt delivery and saved-rationale checks, remains retained but is superseded for this development milestone. The scripted final JSON used the actual ledger state by construction; this tests the integration seam, **not** whether a real model can produce the schema, cover every material claim, recover from rejection or generate useful interpretation.
6. **Paid development probe prepared, not launched.** `run_insight_candidate_development_flash_v1.py --preflight-only` rechecks all source rows and selects FITB, RELY, TFC and VRSK with two fresh sessions each (8 total) in a fixed order, SHA256 `9da12b469a19365e7940a692cc6a5ad0654e15f6f00f771fa307ccceba3244cb`. Twelve prompt/gate/runner tests pass. The runner refuses existing output paths, requires a separate explicit paid-run flag and estimated spend cap, retains failures, and hashes results. Across these four issuers' 20 prior v4 sessions, the observed mean estimated cost was about USD 0.0114 and maximum about USD 0.0309 per session; the new prompt and behavior can change the price, so this is only a planning reference. No v5 model request has been made, and v4 authorization is not reused. This arm is **seen-case development**, not source-distinct confirmation or a statistical reliability estimate.

## Work still needed before a new paid confirmatory arm

- Complete the *coverage contract*: each material quantitative claim in the answer and saved rationale must be represented by a typed assertion, or a reviewer must flag the uncovered span. A validator over submitted claims alone can be gamed by omission. The current typed-candidate gate blocks obvious digit/currency/percentage text outside typed claims but **does not** catch spelled-out amounts, unnumbered comparisons, or unsupported causal claims in its three interpretation fields. It also cannot establish that the model chose all important claims. Publication must remain held when coverage is incomplete, the response is malformed/truncated, a submitted assertion is contradicted, or the ledger disagrees with the final-state claim. Test that broader semantic coverage against known v4 wrong answers and correct controls **without** treating those seen answers as a holdout.
- Add a canonical, ledger-derived state summary to published answers. Model prose may discuss implications, but statements about saved review ID, source attachments, next-review date, decision hold, actionability and alert status must be checked against the actual ledger. The existing read-only v4 state scanner is diagnostic, not yet a publication gate.
- Retain claim-level F/I/R/S/U review for *all* material assertions and qualitative implications. Host arithmetic checks cannot certify that a conclusion is useful, economically relevant or causally justified. Without an independent finance-domain judge, label Codex/LLM judgments as diagnostic, not expert validation.
- Freeze a **source-distinct** future case frame, source-row/period/basis audits, prompts, runtime/plugin hashes, model routing, cost bound, random run order, failure handling and exact case-level statistical gate before observing new answers. Keep event→review, screening→candidate and portfolio-risk results separate; a strong cross-workflow claim needs independent case clusters for each workflow, not reuse of the same issuers or five repetitions treated as five independent cases.
- The v4 pre-ranked source candidate list contained 23 issuers: its 20 selected issuer pairs have now been observed, leaving only RF, MTB and KEY as unused reserves (all in the banking/capital-markets stratum). It cannot by itself supply a new balanced 20-case, four-stratum confirmation panel. A new issuer/period universe and objective ranking must be frozen before selecting filings; do not pad the frame with previously observed v2/v4 cases while calling it source-distinct.
- Obtain separate authorization before any new external model call. The USD 2.00 v4 authorization is exhausted in scope even though actual v4 spending was lower. Existing free development replays do not imply paid-run consent.

The next evidence milestone is a **source-grounded semantic coverage check** over the candidate's qualitative text and saved rationale, followed by a small paid *development* probe of autonomous schema compliance/error recovery under a separate authorization. Only after that and a new source-distinct case frame is a paid confirmatory experiment interpretable as a test of improved insight quality rather than merely another model run.
