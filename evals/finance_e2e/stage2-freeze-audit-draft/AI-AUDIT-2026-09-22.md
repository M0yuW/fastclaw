# Stage 2 AI Technical Audit

## Status and scope

This is an AI-assisted technical review of the 98-item Stage 2 freeze-audit set. It is not a human review and it was not blinded: part of the machine-reference file had already been inspected before this audit. The result is suitable for finding defects, preparing remediation, and reducing later human-review effort. It does not satisfy the current protocol requirement for two independent human reviewers.

The review used the SHA-256-locked local SEC artifacts, the acceptance-time lock, the generated Stage 2 suite, the audit task file, and independent recalculation of every oracle item. The existing reviewer A and reviewer B files were not modified.

## Root cause and experimental impact

`gold_record_groups` calls `fact_is_present`, which treats occurrence of a numeric candidate as evidence coverage. For negative facts it additionally looks for a broad negative marker near the number. It does not require the intended metric, reporting period, unit, accounting basis, or source-fact identity to match.

This is particularly unsafe for common values such as 8, 10, 15, 21, 26, 49, 50, 51, 59, 115, and 2.8. It also allows two distinct facts with the same numeric value to collapse into one identical group, as occurred for Intel Q2 headcount reduction and Intel Q3 gross margin.

If used unchanged, these groups can overstate retrieval recall: a system may retrieve a passage containing the same number in an unrelated context and receive credit for retrieving the required evidence. This affects the quality floor used before interpreting latency, token, or cost improvements.

## Required remediation before formal execution

1. Add explicit `fact_ids` or typed fact spans to generated records and construct equivalence groups from those identifiers rather than raw numeric occurrence.
2. At minimum, require metric, period, unit, basis, and sign-aware contextual matching in addition to the numeric value.
3. Split the merged Intel group into separate Q2 headcount and Q3 gross-margin groups.
4. Regenerate `finance-retrieval-stage2a-v2.json` and the 98-item audit task set.
5. Rerun the full suite-generation and grader tests.
6. Repeat the source/oracle audit on the corrected groups before changing the protocol status to frozen.

## Recommended project-report framing

The formal experiment does not need to establish superior financial analysis quality. A technically stronger and better-supported claim is:

> Under a fixed source snapshot, task, quality floor, and declared model allocation, the FastClaw runtime changes the latency, token, cost, context-replication, observability, and failure-attribution profile of a financial research workflow.

Analysis quality should remain a constraint rather than the principal optimization target. The primary requirement is that the compared mode meets frozen thresholds for strict task completion, evidence recall, numeric grounding, and policy compliance. Conditional on that floor, the report can emphasize:

- end-to-end wall-clock latency and parallel critical-path behavior;
- provider-total and role-specific token use;
- frozen-price estimated cost;
- evidence compression and repeated-context reduction;
- queue, cancellation, correlation, and batch-delegation correctness;
- per-stage and per-role telemetry;
- infrastructure-error rate and failure attribution;
- reproducibility through source locks, pair identifiers, manifests, and retained traces.

This framing remains valid if Team and staged Solo have equal final quality, or if Team is not universally cheaper. The result can be reported as quality-preserving efficiency improvement, no material efficiency difference, or an engineering trade-off. It should not be converted into an unsupported claim that multiple agents inherently reason better.
