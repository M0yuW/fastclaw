# Project Report 中文概要：项目工作、章节内容与实验结果

整理日期：2026 年 11 月 16 日。依据当前英文原稿 `fastclaw_project_report.md` 整理；本文件是内容概要，不是逐句翻译，也不新增实验结论。

当前英文标题：**Design and Evaluation of an Agent Runtime with Financial Research Applications**

中文释义：**面向金融研究应用的智能体运行时设计与评估**。

## 一、项目在做什么

项目实现了一个支持单智能体执行与多智能体协作的运行时，并在其上构建金融研究应用。运行时负责接收请求、管理会话、调度任务、执行工具、协调子智能体、保存状态以及记录执行过程。金融应用负责把这些能力组织成具体研究工作流。

项目不是重新训练金融大模型，也不是自动交易系统。它解决的是：如何让模型能够在受控的软件系统中调用工具、使用证据、完成多步任务，并留下可检查的研究结果。

整体工作可以概括为：

**构建运行时 → 接入金融工具与研究方法 → 实现四类工作流 → 通过工程测试、执行模式比较和真实资料案例评估系统。**

Solo 与 Team 是同一系统提供的两种执行选择。报告不以“多智能体一定比单智能体聪明”为前提，而是考察两者在完成情况、延迟、证据保留和资源使用上的差异。

## 二、主要完成的工作

### 1. 智能体运行时

- 统一外部请求入口，解析用户身份、Agent 权限和会话范围。
- 实现模型调用与工具调用交替进行的执行循环，并支持流式输出。
- 用任务队列控制并发和同一会话的执行顺序。
- 用消息总线连接主智能体和专业子智能体，关联请求与响应，检查循环等待。
- 实现工具权限过滤、取消、超时和迭代限制，并记录错误及终态。
- 保存会话，修复中断后不完整的工具调用历史；较长历史可通过裁剪与摘要压缩。
- 提供任务澄清流程：保存问题、暂停当前轮，收到用户回复后继续。
- 记录模型与工具调用、耗时、token 和估算费用，便于检查执行过程。

### 2. 金融应用能力

金融能力分为三个部分：确定性工具处理数据和计算；Skill 提供可复用的研究方法或数据脚本；模型解释证据并提出研究判断。

应用接入了数据查询、筛选、风险计算、研究观点管理、观察名单和告警等工具。研究账本保存观点、信心水平、证据、复审记录和版本；告警机制处理事件匹配与重复事件。

当已声明的关键指标缺失时，工具规则限制实质性更新，要求进入 `needs_review`。其业务含义是：**原结论和信心水平暂不改变，但暂停将该观点用于后续决策，等待补充证据。**

### 3. 评测与案例分析

项目不仅检查最终回答，还核对实际工具调用、来源和数值、账本变化、告警状态、追踪与费用。评测区分三个层次：

1. **工程执行是否正确**：任务是否执行，调用与状态是否一致。
2. **分析内容是否成立**：事实、计算、推断和风险解释是否有依据。
3. **投资效果是否有效**：是否改善真实投资结果。当前项目没有证明这一层。

## 四、四类应用场景及其工作流

### 1. 财报事件 → 研究观点更新

**问题示例：** 新季度财报发布后，收入、利润率与业务结构变化是否支持修改原有研究观点？

**流程：** 读取原观点和事件告警 → 检查披露数据 → 比较正反证据 → 提出维持、调整、失效或待复审判断 → 写入版本化复审记录 → 确认告警及最终状态。

工程重点是把模型判断与真实账本更新连接起来。金融重点是区分增长、盈利质量和证据不足，不能只看单个积极指标。

### 2. 股票筛选 → 候选研究观点

**问题示例：** 哪些公司满足指定财务条件？看似达标但缺少必填指标的公司是否应进入候选名单？

**流程：** 获取或载入数据 → 检查指标完整性 → 执行确定性筛选 → 解释入选和排除原因 → 按案例要求保存初步研究观点。

工程重点是防止缺失值被当成零，或被模型自行补全。真实资料扩展案例使用 AMD 和 Intel 的冻结 SEC 披露，在两项预设 GAAP 条件下筛选并保存候选观点。

### 3. 投资组合风险诊断

**问题示例：** 组合是否存在集中度风险？持仓信息不完整时，能否依据已知权重判断某个限制一定满足或违反？

**流程：** 读取给定持仓及约束 → 检查数据是否完整 → 调用风险或部分信息边界计算工具 → 解释风险与无法确定的部分 → 提出需要补充的数据。

这类实验采用给定的组合样例，属于只读诊断，不自动调仓。工程重点是把可计算的边界交给工具，避免从不完整持仓推断精确风险。

### 4. 冲突或缺失证据 → 暂停后续决策

**问题示例：** 两份来源对资本开支计划的表述不一致，或事件缺少研究观点要求的关键指标，应如何处理？

**流程：** 保留各来源及日期 → 判断是否已有证据消除冲突 → 未解决时保存待复审状态 → 保持原结论和信心水平 → 暂停后续使用 → 明确所需补充资料。

工程重点是确保回答中“暂缓判断”的表述与实际账本一致，不能只在文字里表示谨慎。

## 五、主要实验结果

以下数字摘自当前报告，不合并不同实验的通过率，也不表示本次重新运行了实验。

### 1. 工程与调度验证

报告记录了核心包测试、完整 Go 测试及部分竞态检查，并记录金融插件的 35 项 Python 测试。测试验证了选定控制路径，并非全面生产可靠性证明。

小规模调度测试使用 48 个模拟任务、12 个会话键，每个会话 4 个任务；并发上限为 1 和 4，各重复 5 次。所有任务完成，同一会话保持提交顺序，峰值执行数未超过限制。总耗时由约 767–773 毫秒降至 192–194 毫秒。这个测试只测队列，不包含真实模型、HTTP 或数据库负载。

### 2. SEC 执行模式比较

主实验包含 24 个配置，每个主要模式重复 3 次，共 216 次主模式观测，另有 48 次诊断观测。

| 模式 | 严格通过 | 基础设施错误 | 已完成输出的平均延迟 |
|---|---:|---:|---:|
| 分阶段 Solo | 55/72 | 2 次模型服务超时 | 70.17 秒 |
| 共享检索 Team | 56/72 | 0 | 31.38 秒 |
| 原始上下文 Team | 63/72 | 0 | 26.51 秒 |

主实验的模型分配不同，不能把速度与费用差异全部归因于协作结构。原始上下文 Team 通过更多，但使用更多 token；共享检索降低了相对资源消耗。

另一个对照让 Solo 和 Team 的所有模型调用均使用 DeepSeek Flash，形成 24 对、共 48 次观测：

- Solo 严格通过 24/24，Team 通过 19/24。
- 平均延迟为 33.62 秒与 22.42 秒，Team 约低 33.3%，且每对都更快。
- Team 平均 token 约高 13.3%，估算费用约高 2.2%。

因此，报告展示的是**执行模式的取舍**：这组任务里 Team 更快，Solo 的严格完成率和证据保留更好。

### 3. 四类工作流重复实验

16 个冻结案例各重复 5 次，共 80 次。SEC 事件类使用历史披露摘录，其余三类使用合成输入。

- 80 次均完成请求，工作流执行检查通过 77 次。
- 初步内容审阅将 54 次评为高质量、13 次充分、13 次存在问题。
- 10 次关键证据缺失场景均记录了复审暂停，保持原状态与信心水平，并阻止后续使用。
- 3 次工作流失败包括只在正文打印工具调用而未实际执行，以及最终说明与保存理由缺少必要数值的情况。

**77/80 是执行检查结果，不是金融分析正确率。** 内容评价属于本地 LLM 辅助诊断，不是独立金融专家评价。

### 4. 真实财报分析案例

较大的真实来源面板保存了 30 家公司、每家 5 次、共 150 次回答和账本副本。自动执行检查标出 101 个可进入定性复核的候选、49 个暂缓项；这不是 101 次高质量分析。原始匿名审阅完成了其中 100 份评分，补充审阅单独记录。

报告重点展示三种分析能力：

| 案例 | 主要洞察 | 与系统工程的联系 |
|---|---|---|
| Marqeta（MQ） | 收入、交易量和调整后 EBITDA 上升，不代表 GAAP 盈利改善；费用增长超过毛利增长 | 将比较项、后续问题和待复审判断关联到来源及账本 |
| AIG | 保险分部调整后业绩改善，与集团 GAAP 利润下降可以同时发生；不能混用两种口径 | 保留分部与集团口径差异，记录证据需求并暂停使用 |
| Repay Holdings（RPAY） | GAAP 亏损收窄主要受到上期减值基数影响，不足以证明持续经营改善 | 结合确定性比较项形成解释，写入复审并核验最终状态 |

MQ、AIG 是检查输出后选出的展示案例。另一个事先选定 MTB、RPAY、CSGP 的研究包含 6 次会话，全部完成工具工作流；内容评价为 1 次高质量、3 次充分、2 次有问题，RPAY 的成功回答来自这一组。

这些研究采用预先核查的来源摘录和数值比较目录。模型的主要贡献是解释比较项、识别相反证据、提出后续研究问题与研究决策，不能把目录中的正确算术全部归功于模型。

### 5. 在线数据到研究账本

一个在线 AMD 案例完成：**Skill 指导数据脚本执行 → 获取带日期的 Nasdaq 日线 → 计算首尾价格变化 → 通过金融插件保存初步研究观点**。

它说明实时数据获取、计算和持久化可以连接成完整链路。单次成功不代表上游长期稳定，也不代表仅凭价格即可形成完整投资结论。

## 六、这些工作能说明什么

报告已有三类互补成果：

1. **工程成果：** 一个支持工具、会话、调度、委派、状态保存和追踪的 Agent runtime。
2. **应用成果：** 四类金融研究工作流，以及真实披露分析和在线数据接入案例。
3. **评测成果：** 将执行正确性、分析质量和持久化状态分开检查，并比较 Solo 与 Team 的效率及资源取舍。

成功案例支持“系统能够产出并保存有用的金融研究分析”。已有错误也表明，不能据此宣称系统能够稳定生成无缺陷的高质量洞察、优于专业分析师或改善投资收益。

## 七、当前主要局限与后续方向

- 测试覆盖不均，部分控制路径仍缺少充分回归验证。
- 调度和委派状态主要保存在单进程内，尚非可持久恢复的分布式执行系统。
- 同一 Agent 的并发、会话事务一致性和长上下文处理仍有改进空间。
- 金融分析解释中仍可能出现错误比较、无依据推断，以及正文与账本状态不一致。
- 实时数据依赖上游可用性；自动发现新披露、连续监控与告警投递尚未被完整验证。
- 内容审阅缺少独立金融专家验证，成功展示案例不能替代整体质量评价。

后续可以围绕这些明确缺口推进，不必为了增加实验数量重复扩展相近案例。

## 八、可用于口头介绍的一段话

我的项目设计并实现了一个支持单智能体与多智能体协作的运行时，重点解决会话管理、任务调度、工具执行、状态保存和执行追踪等工程问题。在应用层，我实现了财报事件复审、候选筛选、组合风险诊断以及冲突或缺失证据处理四类金融研究工作流。我通过工程测试、重复的执行模式对照和真实 SEC 披露案例进行评估。结果展示了不同执行方式的效率与资源取舍，也展示了系统把来源、计算、模型解释和研究账本连接起来的能力。报告选取了盈利质量、分部与集团口径差异、减值基数效应等成功分析，同时保留失败结果，用来说明系统目前的能力范围与改进方向。
