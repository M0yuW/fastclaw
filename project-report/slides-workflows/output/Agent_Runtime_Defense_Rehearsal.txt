01  0:00–0:20  An Auditable Financial Agent Runtime
【指向标题，稍停。】
Good afternoon. I’m Wang Zheyu. I built an agent runtime for financial research. I’ll follow one request from the chat to a saved research record. Then I’ll show how I checked what the system actually did, and what changed when I gave the same task to a team of agents.

02  0:20–0:50  What happens when an analyst sends a request?
【读出问题后，指向 Keep the evidence。】
Imagine an analyst asks, “How did AMD’s closing price change over five trading days? Save the evidence.” That last sentence matters. A percentage answers the first part. For the second part, the system has to keep the prices, their dates and their source so the analyst can check the calculation later. Let’s follow that request into the system.

03  0:50–1:35  How the gateway coordinates a request
【从 Web / API 沿上排指到 Agent loop，再指下方 Tools / plugins 和 Session & traces。】
Start on the left. The gateway identifies the user, the chat and the agent that should handle the request. The queue keeps messages in order within each chat. Other chats can run alongside it, up to a shared limit. Now follow the request down from the agent loop. The model can ask for prices. A tool fetches them. The session trace keeps the call and its result. If the analyst asks to save the evidence, a finance tool also writes a research record. We’ll see both records in the demo.

04  1:35–2:40  How the runtime executes one turn
【只追一次循环。指 run permitted calls，再指回 model。】
Let’s look inside that loop. At the start of a turn, the runtime loads the conversation and repairs any interrupted tool history. It builds the context and gives the model the tools this agent is allowed to use. The context can include a Skill, for example instructions for requesting daily prices. Suppose the model asks for those prices. The runtime executes the call and matches the returned data to the call ID. On the next pass, the model can use the actual figures. A valid final answer ends the turn. If the request is unclear, the system can save a question and pause. A limit on tool iterations also gives the loop a stopping point.

05  2:40–3:35  How Solo and Team divide the work
【指截图的 INPUT 两个分工，再指 OUTPUT 两条回复。】
How does this change with a team? In Solo, one agent works through the stages. In Team, a coordinator can send independent questions to specialists and combine their replies. Here the question was whether AMD’s improvement was broad-based. In the chat, the user can expand the delegation entry. Under Input, one analyst is asked to check growth and the other to look for weaknesses. Under Output, total revenue rose, but Gaming revenue fell. That second result changes what the coordinator can reasonably say. It also gives the user a way to check the conclusion.

06  3:35–4:10  From evidence to research records
【上下两行各指一次，避免逐格读表。】
Here are two jobs an analyst can give the system. After an earnings release, the analyst can ask whether the new figures change an existing thesis. The system reads the thesis and its alert, then saves a review explaining what changed. Screening starts with a different question: which companies meet my criteria? The same thresholds are applied to each candidate, and qualifying names can be saved for follow-up.

07  4:10–4:45  Risk limits and evidence gaps
【指 70% 与 50%，再指第二行的输出。】
Two more workflows show why the output depends on the task. In the portfolio example, one holding makes up seventy percent of the portfolio against a fifty percent limit. The tool flags the breach. In the evidence example, a required figure is missing. The system keeps the existing thesis, records what needs review and blocks its use in later decisions. Now let’s look at an actual run.

08  4:45–5:30  From daily prices to a saved AMD research record
【依次指脚本参数、两个收盘价、保存记录。】
Back to the five-day AMD request. The FinData Toolkit Skill supplied a stock-history script and instructions for using it. The first tool call ran that script and returned five dated Nasdaq price bars. Look at the first and last closes: 570.82 and 534.74. A second call calculated a decline of 6.32 percent. A third call saved the source, dates, prices and calculation together. That was one recorded session. The next example is a separate screen using historical company disclosures.

09  5:30–6:10  AMD and Intel financial screening
【介绍门槛后播放 AMD/Intel 视频。在视频约 00:15 指向展开的筛选输入和输出，约 00:24 暂停。】
The analyst set two rules for this screen: a gross margin of at least forty percent and year-over-year revenue growth of at least zero. Watch the screening entry in the chat. Its input shows those rules. Its output shows that AMD passed both, with fifty percent margin and eighteen percent growth. Intel fell below both thresholds. Now we know which company qualified. How can we check that it was saved?

10  6:10–6:50  The saved AMD research record
【接着播放同一视频。约 00:33 暂停在读回结果，指 AMD、researching 和 version 1，留两秒再继续。】
Here is the write. The next tool reads the record back. Look at the company, status and version: AMD, researching, version one. That is the evidence for the sentence “AMD was saved for further research.” The screening result tells us why AMD qualified. The readback tells us what the system kept. I used that same distinction when I designed the evaluation.

11  6:50–7:25  How the evaluation harness works
【沿 Freeze → Run → Capture → Score 指图。】
For each workflow case, I fixed the inputs and started an isolated session with a fresh ledger. After the run, I kept the answer, the tool trace and the resulting records. Take the missing-evidence case. An answer can say, “We need more information.” To pass the workflow check, the stored review also has to preserve the prior thesis and block its use. I can check those conditions directly in the ledger.

12  7:25–7:55  What counts as a pass?
【先指左侧的 24 pairs，再指右侧的 16 × 5。】
There are two sets of scores to keep in mind. For Solo and Team, I ran eight configurations three times, giving twenty-four pairs with the same model. A strict pass required the milestones, accurate figures and enough supporting evidence in the final answer. Separately, I ran sixteen financial workflow cases five times each. Those checks looked at tool calls, saved state and clean completion.

13  7:55–8:55  Team finished faster, while Solo passed more checks
【先看两张图，停一下，再读 token 和 77/80。】
The trade-off is clearest if we read the two charts together. Solo passed all twenty-four strict checks and averaged 33.62 seconds. Team passed nineteen out of twenty-four and averaged 22.42 seconds. Running specialists in parallel saved about eleven seconds on average. Some final answers, though, dropped a calculation or a piece of evidence when the coordinator combined the replies. Team also used more tokens: about forty-seven thousand per run, compared with forty-one and a half thousand for Solo. Separately, seventy-seven of eighty financial workflow runs passed their execution checks. That last figure measures whether the required actions and state changes occurred.

14  8:55–9:25  Clarification within a conversation
【回指第 4 页讲过的 pause 分支；此处是示意对话。】
One design question remains: what should happen before the system even starts gathering evidence? In this example, “Compare the latest results” leaves out the company and the periods. The agent asks one question and pauses. The user supplies Marqeta and the two quarters in the same chat. This illustrates the clarification branch we saw earlier. Testing that behavior systematically is part of my next work.

15  9:25–10:00  Contributions and next steps
【收尾时看观众。】
I built a runtime that can carry a financial research request through to an inspectable result. The analyst can open a delegation to see who checked what, or read a saved record to verify what changed. The experiments also showed where the design needs work: Team finished sooner, while Solo retained the required evidence more consistently on these tasks. My next priority is to check that evidence survives when specialist replies are combined. Thank you. I’m happy to take questions.
